// ## 🔄 The Lifecycle of Your Hybrid Command Bar

// ```
// [User presses ⌘K] ──> Open Modal ──> Input is empty ("") ──> Render "Recent" + "Categories"
//                                                 │
//                                       [User starts typing]
//                                                 │
//                                                 ▼
//                                     Input has value ("inv")
//                                                 │
//                                                 ▼
//                                     1. Hide "Recent Searches"
//                                     2. Run Fuzzy Filter on Actions/Data
//                                     3. Render Filtered Groups

// ```

// ### 1. The Initial State (Input is Empty)

// The moment the modal mounts, your search query state is an empty string (`""`).

// * **The UI Logic:** Your component detects the empty string and renders your hardcoded default categories (like "Quick Navigation") alongside an array of items fetched from `localStorage` (your "Recent Searches").
// * **Keyboard State:** Focus is automatically forced onto the text input via a React `useRef`. Active selection defaults to index `0` (the very first item in the list).

// ### 2. The Filtering State (As You Type)

// The moment the user types a single character, the component re-renders.

// * **The UI Logic:** You conditionally hide the "Recent Searches" block completely. It makes no sense to show "Recent Searches" if they are actively looking for something new.
// * **The Math:** Your component takes the string (e.g., `"set"`) and runs a filtering function over your entire command dataset.

// > 💡 **The Performance Trap:** If you use a basic Javascript `.filter()` and `.includes()`, a typo like `"sttings"` will break the search. Modern command bars use a **Fuzzy Search** algorithm (like the `fuse.js` library or the built-in filtering in `cmdk`). It calculates a distance score, meaning `"set"` will still surface **"Settings"** and **"Setup Team"**.

// ### 3. The Navigation State (Active Index)

// This is where the keyboard interaction magic happens. You maintain a piece of state called `activeIndex` (an integer starting at `0`).

// * **`ArrowDown` Key:** Intercepts the default page scroll, increments `activeIndex` by 1, and applies a highlighted background class (like `bg-zinc-100` or `dark:bg-zinc-800`) to the item matching that index.
// * **`ArrowUp` Key:** Decrements `activeIndex` by 1.
// * **`Enter` Key:** Looks at the item at `dataSet[activeIndex]` and triggers its specific action—whether that's routing to a new page (`router.push('/dashboard')`) or opening a modal.

// ---

// ## ⚠️ The Sneaky Edge Cases to Code For

// Since you are building this for a UI library, watch out for these three bugs that plague homemade command bars:

// 1. **The Invisible Selection:** If your list is long and scrollable, hitting `ArrowDown` might move the selection to an item *below the fold* where the user can't see it. You have to use a utility (or `element.scrollIntoView({ block: 'nearest' })`) to make sure the container scrolls automatically with the keyboard selection.
// 2. **The Category Header Trap:** Your `ArrowDown` loop needs to be smart enough to **skip** category headers. The user shouldn't be able to "select" the words "ACTIONS" or "RECENT SEARCHES"—the highlight should skip right over them to the next actual interactive item.
// 3. **The Dynamic Array Shortening:** If your filtered list drops from 10 items down to 2 items because the user typed something highly specific, and your `activeIndex` was sitting at `7`, your app will crash (reading undefined). Every time the input changes, you have to reset `activeIndex` back to `0`.
